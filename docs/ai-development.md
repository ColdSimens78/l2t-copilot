# Как я разрабатывал этот проект: методология агентной разработки

Я — автор и мейнтейнер этого репозитория. Ниже — как устроен мой
процесс: команда AI-агентов, спецификации впереди кода, ревью каждого
коммита, и почему это дало рабочий продукт за три дня, а не прототип
за три месяца.

## Отправная точка

Гипотеза, которую я проверял: **если разграничить зоны ответственности,
агенты способны довести продукт до продакшена, а не только до прототипа.**
Условия, которые я себе поставил:

- спецификация каждой части написана **до** кода этой части;
- каждый коммит проходит тесты и моё ревью;
- каждая внешняя зависимость проходит проверку лицензии по содержимому
  файла, а не по бейджу на сайте;
- каждая ошибка в процессе фиксируется как правило, а не как «бывает».

## Команда

Пять ролей, каждая — отдельная агентная сессия со своей зоной
ответственности и границами:

- **Lead** (это я как оператор процесса) — архитектура, декомпозиция,
  ревью всех коммитов, релизы, финальные решения;
- **Desktop Engineer** — Rust: ядро `l2t-core`, интеграция движка,
  Tauri-команды;
- **Frontend Engineer** — кокпит: React/Tauri, экраны, призрачные ноты;
- **OSS Scout** — постоянная разведка: библиотеки, лицензии, конкуренты,
  состояние апстримов;
- **UX Architect** — спецификации экранов и метрик до реализации.

Координация — без переписки: общий файл памяти с append-only статусами
и общие документы в репозитории. Каждый агент начинает работу с чтения
контекста и заканчивает — записью результата. Прямые контакты между
агентами исключены конструктивно: их не существует.

## Роли против «стада агентов»

Частая ошибка агентной разработки — запускать десять сессий «делай
фичу». Я делаю наоборот: у каждой роли узкая специализация, своя область
владения файлами (Backend не трогает `ui/`, Frontend не трогает
`src-tauri/`) и свой тип задач. Конфликты исключаются не коммуникацией,
а границами: интерфейс между ядром и интерфейсом зафиксирован отдельным
документом-контрактом с версиями, и обе стороны обновляются синхронно.

## Конвейер

```
Founder: видение, продуктовые решения, приёмка
   ▼
Lead: декомпозиция → спецификация → задача → ревью → релиз
   ▼                          ▼                    ▼
Desktop Engineer      Frontend Engineer      Scout / UX Architect
```

1. **Продуктовая спека** — метрика успеха (Acceptance Rate — доля
   сгенерированных партий, которые пользователь оставил в аранжировке)
   сформулирована до первой строки кода.
2. **UX-спецификация** — состояния, переходы и маппинг «кнопка → команда»
   для каждого экрана; Frontend Engineer строит интерфейс, не задавая
   вопросов.
3. **Контракт ядра↔интерфейса** — типы в одном документе, Rust- и
   TS-стороны обновляются одним коммитом.
4. **Реализация** — scoped-коммиты (явные пути файлов, никакого
   `git add -A`), тесты рядом с кодом, CI (pytest + cargo) на каждый push.
5. **Ревью** — каждый коммит читается, сверяется со спекой и контрактом;
   найденное — в правки того же коммита.

## Что это дало на практике (проверенные случаи)

- **Выбор движка.** Вместо «взять популярное» — верификация 15+ кандидатов
  по чек-листу из девяти требований. Результат: permissive-сессионного
  движка, кроме SoundCraft и Tracktion (GPL/коммерческая стена), на рынке
  нет; migration не оправдана; найден headless-путь к SoundCraft с
  холодным стартом 0.15 с против 8 с через GUI-плагин.
- **Безопасность зависимостей.** Список из семи предложенных MCP-серверов:
  после проверки — два имени не существуют вовсе, один проект без
  LICENSE-файла при «MIT»-бейдже в README, один дублирует нашу
  мультиагентную систему. В проект не попал ни один; правило «NOVERIFY =
  reject» зафиксировано.
- **Ошибки в правила.** Импорт MIDI с чужим темпом молча перезаписывал
  темп-карту сессии → генераторы перестали вшивать tempo (контракт
  `embed_tempo=False`), а поведение задокументировано. Паника анализатора
  на коротких файлах → ядро композитом обходит сломанный путь, обход
  верифицирован тестами.

## Границы методологии (честно)

- **Человек — владелец решений.** Агенты предлагают, я ратифицирую
  архитектурные развороты и принимаю продукт. Автономность агентов
  ограничена протоколами и правами.
- **Ревью обязательно.** Без чтения кода коммит не проходит — это мой
  главный контроль качества, а не формальность.
- **Модель — инструмент под задачу.** Творческий UI и чётко
  специфицированный Rust требуют разных моделей и разной степени
  детализации задачи; спецификации я пишу глубже для «лёгких» моделей.

## Воспроизводимость

Никаких приватных платформ: агентный редактор (у меня ZCode), GitHub,
Tauri, React, Rust, Python, MCP. Вся дисциплина — из этого документа:
спецификации впереди кода, контракты с версиями, scoped-коммиты,
CI-гейты, разведка перед зависимостями, ревью каждого коммита.
