# Предложение по архитектуре AI-нативного интерфейса L2T

**Версия:** 0.1 (черновик на ревью «Папе»)
**Автор:** дочерняя сессия «Исследователь UI»
**Дата:** 2026-11-22
**Статус:** не коммичено, ожидает ревью

---

## 0. Резюме (TL;DR)

**Рекомендуемый паттерн: «Кокпит над шиной» (Copilot Cockpit).**

L2T не строит свою DAW и не прячется в чат. L2T — это **отдельное нативное
окно-спутник рядом с DAW**: три режима (**Loop X-Ray → Стейджинг →
Self-Check**) плюс постоянно видимая **консоль агента с живым логом MCP-шины**.

Ключевая идея, объединяющая всё предложение:

> **UI — это проекция MCP-шины.** Каждая кнопка = MCP-инструмент, каждый
> вызов агента = строка в логе, каждое состояние = файл в workspace.
> Cockpit не имеет собственной скрытой логики — он визуализирует шину и
> файлы, а командовать может и человек (кнопками), и внешний агент (ZCode),
> и будущий локальный «Мозг» (qwen_bridge). Это зеркальное отражение девиза
> SoundCraft «всё кликабельное — скриптуемо»: **всё скриптуемое — кликабельно**.

Технология: **egui (Rust)**, как у SoundCraft — одна экосистема, нативное
аудио-превью, локальность. Web-панель — осознанно отложена (см. §7).

## 1. Исследование: чему учимся у существующих DAW

### 1.1 FL Studio — паттерн «слои + аранжировка» (обязательный разбор)

FL Studio построен вокруг триады **Channel Rack → Piano Roll → Playlist**:

- **Channel Rack** держит инструменты («каналы») и **step-секвенсор**: клетка
  = 16-я нота, клик = удар/нота. Паттерн длиной 1–512 шагов (1/16 — 64 такта
  в 4/4). Ключевая особенность: **паттерн — это данные всех каналов сразу**
  (степы + партии Piano Roll + автоматизация), а не одного инструмента.
- **Piano Roll** — лучший в индустрии редактор нот per-channel; в нём видны
  «призраки» (ghost channels) — бледные ноты других каналов для сведения
  гармонических слоёв.
- **Playlist** — аранжировка, где **паттерны ложатся как клипы** (Pattern
  Clips): каждый элемент (биты/бас/аккорды) — отдельный паттерн, паттерны
  стакаются на разных дорожках, такты собираются в песню. Picker Panel —
  библиотека паттернов с drag-and-drop.

**Что берём для L2T (это ДНК нашего стейджинга, §3.2):**
1. **Партия = короткий переиспользуемый паттерн-слой** — ровно так работают
   наши midi-gen генераторы (1-тактовые бас-паттерны, 4-тактовые прогрессии,
   барабанные лупы с филлами). Стейджинг L2T = «Channel Rack для
   сгенерированных партий».
2. **Просмотр слоя без открытия редактора** (мини-превью нот прямо в стойке,
   как степы/мини-скролл в Channel Rack) — пользователь видит, что ему
   предложили, не покидая кокпит.
3. **Слоистая аудиция**: mute/solo на слой — комбинируем «луп + бас + аккорды»
   на слух до любого импорта.
4. **Паттерн → аранжировка как отдельный шаг**: у нас этот шаг = «заполнить
   N тактов» (наш рецепт `duplicate_extend`, правило 6 шины) и раскладка в
   DAW — то есть FL-шный переход Channel Rack → Playlist.

**Что НЕ берём:** «паттерн содержит все инструменты сразу» — нам нужна
обратная семантика (партия = отдельный MIDI-файл = отдельный слой = отдельная
дорожка в DAW), потому что наша ценность — редактируемость каждой партии
по отдельности.

### 1.2 Ableton Live — клип-парадигма (Session View)

Session View: колонки = треки, строки = сцены; клипы запускаются синхронно
глобальному темпу (launch quantization), сцена = комбинация слоёв одним
нажатием, Follow Actions автоматизируют переходы, джем в Session
записывается в линейный Arrangement.

**Что берём:**
1. **Аудиция по клипам до коммита**: сгенерированная партия = «клип в
   холдиг-арии», который запускается в синхронном лупе — как клип Session
   View, но ещё не в проекте. Это главный механизм «показать ДО импорта».
2. **Комбинации слоёв = сцены**: кнопка «▶ всё вместе» и пресеты комбинаций
   (луп+бас / луп+бас+аккорды+бит) — сценический способ сравнить варианты.
3. **Черновик → финал как два режима**: стейджинг (нелинейный джем с
   генератором) → импорт в DAW (линейная аранжировка). Мост «Record to
   Arrangement» у нас = кнопка «Импорт принятых».

**Что НЕ берём:** Session View как основную форму главного окна — наш
линейный аранжировщик уже есть (SoundCraft), дублировать его не нужно.

### 1.3 Bitwig Studio — модульность и The Grid

Bitwig: Poly Grid / FX Grid / Note Grid (160+ модулей), модуляторы вешаются
почти на любой параметр, сигналы Grid взаимодействуют с DAW-уровнем —
философия «всё модульно, всё модулируемо». Note Grid примечателен: **ноты —
это тоже патчуемые данные**.

**Что берём (на уровне философии, не UI):**
1. **Компонуемость = наша MCP-шина.** «Всё модульно» у нас уже есть: уши
   (audio-analyzer), руки (midi-gen), тело (DAW), мозг (qwen_bridge). Задача
   UI — **показать композицию явно**: лог шины делает модульность видимой
   (как патч-корды Grid видны на экране).
2. **Note Grid-настройка**: партия как данные (MIDI-файл + JSON-параметры),
   которые можно пере-параметризовать (style/voicing/variation) — наши
   chips-регенерации (§4.1) — это «патчинг нот».

**Что НЕ берём:** визуальный патчинг как форму интерфейса — для целевой
аудитории (продюсеры, не модульные синтезаторы) это лишний слой абстракции.

### 1.4 SoundCraft — наш хост

SoundCraft (storytold/soundcraft): чистый Rust, **egui** (`soundcraft-ui-egui`,
слоистая архитектура — «ниже UI ничего не знает про egui», GUI заменяем),
Pro Tools-подобные окна Edit/Mix, MIDI-редактор, перемещаемые/докуемые
панели, 120 fps при ~70 треках. Главное для нас: **каждое кликабельное
действие = команда с JSON-параметрами** (CLI, JSON-канал, **MCP-сервер**),
headless-режим, скриншоты, `session.inspect` для самопроверки агента.
Лицензия MIT/Apache-2.0 (форки обязаны убрать товарные знаки). Статус
pre-alpha (~40 % пути), т.е. API будет дрейфовать — учтено в §7/§8.

**Что берём:** SoundCraft остаётся **единственным редактором и микшером** —
весь note-эджитинг и микс после импорта живут там. Cockpit не конкурирует с
DAW, а готовит материал для неё. Плюс «всё кликабельное — скриптуемо»
зеркалим в «всё скриптуемое — кликабельно».

### 1.5 MAGDA — референс AI-нативной DAW

MAGDA (Conceptual-Machines/magda-core, magda.land): «Multi-Agent Digital
Audio Workstation», C++23/JUCE, GPL-3.0, активная разработка с января 2026.
Как они встроили AI в UI:

- **AI-чат панель** слева (рядом с Inspector); справа браузеры; снизу
  контекстный редактор; три вида — Arrangement / Session / Mix.
- Агенты работают по схеме **«чат → LLM генерирует DSL → DAW исполняет DSL
  прямо в проекте»**; DSL видим пользователю. BYOAK (свои API-ключи) или
  локальный llama.cpp.
- Агенты **читают сессию и действуют** через DSL: промпт-в-паттерн в
  MIDI-секвенсоре, агент сведения («измерь микс и ответь по цифрам»),
  similarity-поиск в медиатеке, автоматизация по запросу.
- **MCP endpoint + WebSocket + OSC** — внешние AI-хосты могут рулить MAGDA.

**Что берём (главные уроки):**
1. **Команды агента видимы и инспектируемы** (их DSL) — у нас эту роль играет
   лог MCP-вызовов. Никаких невидимых мутаций проекта.
2. **Агент видит состояние сессии перед действием** — наш pull-принцип
   (`get_session` перед действием) уже в DawBackend.
3. **MCP-endpoint для внешних хостов** — мы и есть MCP-native, cockpit
   лишь должен не прятать шину за собой.

**Чего избегаем:** MAGDA — это **целая DAW** (GPLv3, свой движок, свой UI).
Мы сознательно идём другим путём: не строим DAW вокруг агента, а строим
**агентный слой над существующей DAW**. Наша ценность — AI-слой, тело
сменное (философия DawBackend).

## 2. Рекомендуемый UI-паттерн: «Кокпит над шиной»

### 2.1 Почему не альтернативные формы

Рассмотрены три формы верхнего уровня:

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **(а) Панель внутри SoundCraft** (оверлей-патч) | Один процесс, нативный док | Привязка к одному хосту (против философии DawBackend); патч расходится с апстримом; UI-слой SoundCraft — чужая территория, которую мы обещали не форкать | ❌ пока |
| **(б) Отдельное окно-«кокпит» над MCP** | Хост-агностик; нулевое вмешательство в DAW; шина видима целиком; работает даже без DAW (анализ+генерация) | Два окна на экране | ✅ **рекомендовано** |
| **(в) Только чат/терминал (статус-кво)** | Уже работает; агент-нативным юзерам хватает | Нет аудиции до импорта, нет визуализации анализа, высокий порог для «волны 2+»; Acceptance Rate нечем измерять жестом | ✅ остаётся как режим power-user |

Вариант (б) не отменяет (в): **cockpit — это проекция того же самого**, что
можно делать из чата. Ничего эксклюзивного для GUI не создаётся.

### 2.2 Четыре принципа кокпита

1. **Кнопка = MCP-инструмент.** Каждый элемент UI вызывает тот же
   инструмент, что доступен агенту из чата/CLI. Обратное тоже верно: всё,
   что агент может сделать, имеет кнопку. Нет скрытых возможностей.
2. **Лог шины = истина.** Правая колонка — живой лог всех MCP-вызовов
   (команда, параметры, статус, время). Это «инспектор DSL» в духе MAGDA и
   гарантия прозрачности из PRD.
3. **Превью ≠ коммит.** Ничто не попадает в DAW-сессию без явного
   «Принять». Аудиция идёт в кокпите (свой лёгкий синт), финальная проверка
   звука — в DAW. Импорт — всегда жест человека (или явно включённый
   автопилот с лимитами).
4. **Workspace = состояние.** Стейджинг персистится файлами в workspace
   (.mid + manifest.json с версиями и статусами). Перезапустил кокпит —
   увидел то же самое. Нет скрытой БД состояния UI (правило 1 шины).

### 2.3 Общая схема

```
 рабочее место музыканта (один экран, окна рядом или тайлинг)
┌──────────────────────────────────┐  ┌──────────────────────────────────┐
│  SoundCraft (или др. DawBackend) │  │  L2T Cockpit (egui)             │
│  ═══ редактор и микшер ═══       │  │  ═══ копилот над шиной ═══      │
│                                  │  │                                  │
│  timeline / клипы / ноты         │  │  [Loop X-Ray][Стейджинг][Check] │
│  фейдеры, плагины, автоматизация │  │  ┌────────────┬───────────────┐ │
│  ──────────────                  │  │  │ панель     │ консоль агента│ │
│  сюда прилетают ПРИНЯТЫЕ партии  │  │  │ режима     │ + лог шины    │ │
│  (MIDI-дорожки, редактируемые)   │  │  │ (§3)       │ (chat+MCP)    │ │
│                                  │  │  └────────────┴───────────────┘ │
└───────────────▲──────────────────┘  └───────────────┬──────────────────┘
                │      DawBackend: import_midi,        │
                │      get_session, set_tempo, render  │
                └────────────── MCP-шина ──────────────┘
                        audio-analyzer · midi-gen · (qwen_bridge)
                     данные (WAV/MIDI/JSON) ходят через workspace
```

Кокпит — **MCP-хост**: он сам порождает/подключает серверы шины и раздаёт
команды. Кто «держит штурвал», кокпиту безразлично: нажатие кнопки (человек),
запрос из внешнего агента (ZCode), локальный мозг (qwen_bridge) — в логе
виден только эмитент команды.

## 3. Панели и режимы

Три режима слева + постоянная консоль справа. Режимы — это воронка
hero-сценария из PRD: **понять луп → послушать варианты → проверить**.

### 3.1 Loop X-Ray (анализ лупа)

Первая остановка: «брось луп — узнай, что это». Карточка-отчёт поверх
реального выхода audio-analyzer (числа — из наших проверенных прогонов):

```
┌─ Loop X-Ray ──────────────────────────────────────────────────────┐
│  📥  перетащи WAV/FLAC сюда            [переанализировать]        │
│ ───────────────────────────────────────────────────────────────── │
│  loop.wav · 32.0 s · 44.1 kHz · mono                               │
│                                                                    │
│  TEMPO       60.1 BPM   уверенность ▓▓▓▓░░ 64%   (альтернатива:    │
│                        120.2 — возможно ×2 по хэтам [выбрать 120])│
│  KEY         A minor   уверенность ▓▓▓▓▓░ 91%  ≡ C major (отн.)   │
│  LOUDNESS    −12.0 LUFS · TP −2.4 dBTP                             │
│              цель: [Spotify −14 ▾]  до цели: +2.0 dB              │
│                                                                    │
│  СПЕКТР (что не так):  суб-бас ▁ низкие ▃ средние ▂ верх ▁        │
│  → «лупу не хватает низа и воздуха — сгенерировать бас и воздух»  │
│                                                                    │
│  РИТМ       onset-плотность 2.1/долю → рекомендация: hat 8-е,     │
│             прямая бочка; свинг 0%                                │
│ ───────────────────────────────────────────────────────────────── │
│  [✓ Применить к сессии: 60 BPM + key-маркер Am]   ← opt-in, #1702 │
│  [→ В стейджинг: сгенерировать партии]                            │
└────────────────────────────────────────────────────────────────────┘
```

Дизайн-решения:
- **Уверенность — гражданин первого класса.** Урок PoC: значения с низкой
  уверенностью нужно интерпретировать, а не цитировать. Всё ниже ~70 %
  рисуется приглушённо + человеческая интерпретация.
- **×2-темп — это фича панели, а не бага анализатора**: обе гипотезы (60/120
  от hat onset-lock — реальный случай из наших тестов) показываются
  рядом, выбор за человеком.
- **Relative-key эквивалентность видна сразу** (A minor ≡ C major) — правило
  7 шины, отлитое в `keys_match`, здесь просто визуализируется.
- **Спектр → действие**: панель не просто показывает полосы, а связывает
  провал в полосе с конкретной генерацией (суб-бас ↓ → «сгенерировать
  бас»). Это мост в Стейджинг.
- **Adopt Loop Settings = явный диалог**, не автоприменение (правило 4:
  сессия — источник истины; opt-in половина issue #1702).
- Полоса секций (intro/drop/…) появится, когда апстрим починит panic в
  sections.rs (наш issue #3 у JuzzyDee).

### 3.2 Стейджинг (сердце интерфейса)

«Channel Rack для сгенерированного» (FL) + «клипы до коммита» (Ableton).
Каждая партия — **слой-карточка**: мини-превью нот, параметры генерации как
chips, версия, кнопки аудиции/регенерации/приёмки.

```
┌─ Стейджинг · loop.wav 60 BPM A minor ──────────────────────────────┐
│ СЛОИ (луп всегда внизу как референс)                               │
│ ┌────────────────────────────────────────────────────────────────┐ │
│ │ 🎸 bass      v2  ▶ ─●──●──●──●──●─  [style: syncopated ×]      │ │
│ │   A minor · 5 нот · off-beats 1.5s/3.5s      [↻] [✓] [✕]       │ │
│ │   история: v1 basic → v2 syncopated         ⏳новое            │ │
│ ├────────────────────────────────────────────────────────────────┤ │
│ │ 🎹 chords   v1  ▶ ─▬▬──▬▬──▬▬──▬▬─  [voicing: voiceled ×]      │ │
│ │   Am/C · F/C · C · G/D · движение 4         [↻] [✓] [✕]        │ │
│ │   история: v1 voiceled (motion 4 < block 7) ⏳ прослушано       │ │
│ ├────────────────────────────────────────────────────────────────┤ │
│ │ 🥁 drums    v1  ▶ ─●●●●●●●●●●●●─  [style: basic][fill: 4-й такт]│ │
│ │   kick 1&3 · snare 2&4 · hats 8-е           [↻] [✓] [✕]        │ │
│ └────────────────────────────────────────────────────────────────┘ │
│ 🎵 loop.wav (источник)  ▶ ─▬▬▬▬▬▬▬▬▬▬▬▬─  🔒 референс, не трогаем  │
│ ────────────────────────────────────────────────────────────────── │
│ СЦЕНЫ:  [луп+бас] [луп+бас+аккорды] [всё] [▶ прослушать выбранное]  │
│                                                                    │
│ ДЛИТЕЛЬНОСТЬ АРАНЖИРОВКИ: [8 тактов ▾]   ← кокпит сам разложит      │
│                                            (ceil(log2 N) дублей,    │
│                                             правило 6)             │
│                                              [⤓ Импорт принятых →] │
└────────────────────────────────────────────────────────────────────┘
```

Дизайн-решения:
- **Статусы аудита на карточке** — это и есть сырьё Acceptance Rate:
  `⏳ сгенерировано → ◀ прослушано → ✓ принято / ✕ отклонено`. История
  версий сохраняется (v1 не удаляется регенерацией — можно вернуться;
  «принять v1 после того как послушал v3» — реальный сценарий).
- **Мини-превью нот/степов без открытия редактора** — дух FL. Для барабанов
  — GM step-грид, для баса/аккордов — piano-roll-полоска.
- **Chips = реальные параметры midi-gen** (`style`, `voicing`, `variation`,
  `bars`). Клик по chip = регенерация с другим значением; menu chip =
  выпадающий список. Кнопка = MCP-вызов `midi-gen.generate_*`.
- **Аудиция**: быстрый превью-движок кокпита (лёгкий синт, §7) — луп
  крутится, слои включаются/выключаются на лету, всё синхронно темпу.
  Альтернативный прогон «в звуке DAW» — см. ниже.
- **Двухступенчатая аудиция** (честно про звук):
  1. *быстрая* — превью-синт кокпита (мгновенно, для итераций регенерации;
     Import в SoundCraft шёл по ~10 с — слишком долго для перебора
     вариантов);
  2. *WYSIWYG* — «прослушать в DAW»: агент импортирует в карантинную
     staging-группу треков (muted, за пределами аранжировки), где звучат
     настоящие `subtractive_synth`/`drum_synth`. Не понравилось — undo.
- **«Импорт принятых»** — единственная кнопка, меняющая DAW-сессию: для
  каждого ✓-слоя `daw.import_midi` + инструмент назначается хостом
  (SoundCraft делает это сам). Дальше ноты принадлежат человеку (PRD:
  «вы владеете каждой нотой» — редактирование уже в SoundCraft).
- **Длительность** выбирается намерением («8 тактов»), а не механикой
  дублей — кокпит прячет экспоненциальный `duplicate_extend` за интентом.

### 3.3 Self-Check (проверка результата)

Появляется после bounce. A/B-отчёт «луп → микс» на реальных числах нашего
полного теста:

```
┌─ Self-Check ───────────────────────────────────────────────────────┐
│  bounce_v3_full.wav · 32.0 s · −21.2 LUFS · peak −6.8 dB           │
│ ─────────────────────────────────────────────────────────────────  │
│  ПОКАЗАТЕЛЬ      ЛУП          МИС         ВЕРДИКТ                  │
│  Тональность     A minor      A minor 0.84  ✓ (≡ C major — отн.)   │
│  Темп            60.1         60.1          ✓                       │
│  Громкость       −12.0 LUFS   −21.2 LUFS    ⚠ до Spotify −14:      │
│                                             +7.3 dB [normalize]    │
│ ─────────────────────────────────────────────────────────────────  │
│  ЧТО ДОБАВИЛИ СЛОИ (Δ по полосам):                                 │
│  суб-бас +5.7 · низкие +6.7 · средние +6.5 · верх +2.1 dB           │
│  → «слои заполнили ровно те полосы, которых лупу не хватало» ✓     │
│  (план из Loop X-Ray выполнен)                                     │
│ ─────────────────────────────────────────────────────────────────  │
│  ИТОГ: ✅ сходится · трек готов к сведению/мастерингу              │
│  [normalize до цели] [→ досдать в DAW] [отчёт .html в workspace]   │
└─────────────────────────────────────────────────────────────────────┘
```

Дизайн-решения:
- **Verdict — трёхцветный, но с толкованием**: ✓ / ⚠ (относительная
  тональность, ×2-темп, громкость до цели) / ✗ рассинхрон. Правило 7
  (relative-key + перепроверка тональности ПОСЛЕ аранжировки) —
  пользовательская формулировка, зашитая в UI: чек выполняется по кнопке
  «Проверить микс», т.е. всегда после завершения аранжировки.
- **Самопроверка агента ≠ решение агента**: вердикт — данные для человека.
  «Трек готов к мастерингу» — фраза ассистента, кнопки — у человека.
- **Замкнутость контура наглядна**: панель показывает Δ полос против
  «диагноза» из X-Ray — «план → исполнение» видно одним взглядом. Это
  визуализация нашего A/B-compare (реальный инструмент
  `mcp__audio-analyzer__compare`).
- **Экспорт отчёта** — статичный HTML в workspace (шеринг/архив; единственная
  web-поверхность, см. §7).

### 3.4 Консоль агента и лог шины (правая колонка, всегда видна)

```
┌─ Консоль агента ──────────────────────┐
│ ┌───────────────────────────────────┐ │
│ │ [ты]  сделай бас синкопированным  │ │
│ │ [L2T] midi-gen.generate_bassline  │ │
│ │        {key:"Am", style:"syncop…  │ │
│ │        "} → bass_v2.mid · 0.3 s ✓ │ │
│ │ [L2T] обновил слой «bass» до v2.  │ │
│ │       Послушать?  [▶] [всё вместе]│ │
│ └───────────────────────────────────┘ │
│ ─ лог шины ────────────────────────── │
│ 12:01:03 soundcraft.get_session ✓ 40ms│
│ 12:01:04 midi-gen.bassline …     ✓0.3s│
│ 12:01:31 soundcraft.import_midi  ⏱30s │
│           → inspect: трек 7, 4 ноты ✓│
│ ──────────────────────────────────── │
│ [ввод…                          ] ⏎  │
└───────────────────────────────────────┘
```

- Верх — **чат** (человеку), низ — **лог** (машине). Ответ агента всегда
  показывает инструмент и параметры, которые он вызвал (урок MAGDA:
  инспектируемый DSL).
- **Таймаут ≠ отказ — видно глазами** (правило 2): строка лога меняет
  статус ⏱ → авто-`inspect` → ✓, а не молчаливый ретрай.
- Каждое сообщение агента с действием несёт inline-кнопки ([▶] [принять]
  …) — чат не требует прыгать в панели.

## 4. Роль агента в UI

### 4.1 Чат, карточки-предложения, регенерация

- **Предложение = карточка с кнопками, а не голый текст.** «Бас звучит
  статично (все ноты на сильных долях). Сделать синкопированным?»
  `[Да, style=syncopated]` `[Другой стиль ▾]` `[Оставить]`.
- **Регенерация = видимый diff параметров**, а не «заново»:
  `style: basic → syncopated`, и когнитивно, и в логе. Пользователь всегда
  знает, **что именно** изменится — это управление теми же параметрами
  midi-gen v3 (`style/voicing/variation/bars`), просто без JSON.
- **Проактивность мягкая**: агент предлагает (после аудиции слоя, после
  Self-Check), но кнопка применения — у человека. Единственный
  автоматический контур — явно включённый **автопилот** (§4.2).
- **Undo-культура**: каждое действие агента в DAW откатываемо (undo хоста),
  слои стейджинга одноразовые по природе. Человеку нечего бояться «принять
  на пробу».

### 4.2 Три режима управления и слот «Мозг»

| Режим | Кто издаёт команды | Cockpit показывает |
|---|---|---|
| **Ручной** | Человек кнопками (без всякого LLM) | Кнопки = MCP-инструменты; лог пишет всё |
| **Агент** | Внешний агент (ZCode/Claude/Cursor) через шину | Команды агента светятся в логе; его предложения — карточками в чате |
| **Автопилот** | Локальный мозг qwen_bridge гоняет полный контур (анализ→генерация→импорт→Self-Check) | Каждый шаг подсвечивается в воронке X-Ray→Стейджинг→Check; стоп-кран всегда виден |

Принципиально: **командный язык один** (MCP JSON), эмитентов может быть
много. qwen_bridge встаёт в тот же слот без изменений UI — просто ещё один
эмитент в логе. Режим «Ручной» гарантирует: LLM-даунтайм не выключает
продукт (детерминированные инструменты — граждане первого класса).

Автопилот — визуализация hero-сценария PRD: шаги воронки загораются по мере
исполнения, в конце — карточка Self-Check с вердиктом. Ограничения
автопилота (какие партии, сколько регенераций, импортировать ли самому)
задаются переключателями до старта.

## 5. UX-граница: что человеку, что агенту

Философия: **«агент предлагает — человек располагает»**. Граница проведена
так, чтобы микс и финальные решения были неприкосновенны (это же не-цели
контракта DawBackend: нет микширования и редактирования нот через контракт).

| Область | Человек | Агент |
|---|---|---|
| Анализ лупа | читает интерпретации, выбирает между гипотезами (60 vs 120) | считает, толкует, предлагает |
| Настройки сессии | **согласие** (adopt loop settings — диалог) | готовит точные значения |
| Генерация партий | слушает, сравнивает версии, **принимает/отклоняет** | генерирует, параметризует, итерирует |
| Импорт в DAW | **жест «Импорт принятых»** | механика импорта, инструменты, карантин-полоса |
| Ноты | **владелец после импорта** (правка в SoundCraft) | не редактирует ноты (только регенерирует файл) |
| Аранжировка | **структуру утверждает** (сколько тактов, что где) | предлагает (дубли, филлы, дозаполнение) |
| Микс | **только человек** (фейдеры/пан/плагины в DAW) | не лезет (нет инструментов и в контракте) |
| Мастеринг-целы | выбирает пресет (Spotify/Apple/−) | считает дельты, предлагает normalize |
| Self-Check | читает вердикт, решает что дальше | измеряет, сравнивает, объясняет |
| Уборка | — | имена файлов, версии, маркеры, manifest |

Проверка границы на прочность: агента невозможно заставить необратимо
испортить работу — всё в DAW откатываемо (undo), стейджинг одноразовый,
баунсы не перезаписывают исходник (workspace, версионирование имён).

## 6. Соответствие контракту шины и ценностям PRD

### 6.1 Семь правил шины → элементы UI

| # | Правило | Как проявляется в UI |
|---|---|---|
| 1 | Workspace — граница песочницы | Стейджинг = визуализация workspace: карточки = .mid-файлы + manifest.json; «UI без скрытой БД» |
| 2 | timeoutMs; таймаут ≠ отказ | Строка лога: ⏱ → авто-inspect → ✓; никакого молчаливого ретрая |
| 3 | Паника → JSON-RPC error | Ошибка = toast с причиной, а не крутящийся спиннер навсегда |
| 4 | Сессия — источник истины | Adopt Loop Settings = явный диалог; генераторы без set_tempo (embed_tempo=false) — в chips это видно |
| 5 | Lifecycle движка | Прогресс «поднимаю редактор DAW…» (прогрев ~8 с) — как wake-up паттерн; retry с видимой попыткой № |
| 6 | duplicate_extend экспоненциально | Кнопка-интент «8 тактов» прячет ceil(log2 N); в логе — честные вызовы |
| 7 | Self-Check: relative-key + после аранжировки | Бейдж «A minor ≡ C major (отн.)»; Check запускается по кнопке после баунса готовой аранжировки |

### 6.2 Ценности PRD → механизмы UI

| Ценность | Механизм |
|---|---|
| Скорость | Анализ 55–91 мс — карточка X-Ray появляется мгновенно; регенерация < 1 с; быстрый превью-синт вместо 10-с импортов |
| Редактируемость (главный дифференциатор) | Импорт = обычные MIDI-дорожки DAW; «владение нотами» начинается в момент «Принять»; превью ничего не портит |
| Музыкальная глубина | Chips параметров = управляемая глубина (style/voicing/variation); история версий поощряет итерации до «хочу оставить» |
| Прозрачность | Лог шины = вся деятельность агента; кнопка = инструмент; open-source стек без скрытых API |

### 6.3 Acceptance Rate как жест

Метрика PRD рождается в стейджинге, и UI делает её **честным жестом**, а не
телеметрией-шпионажем:
- `✓ Принять` (или импорт без отклонения) = accepted; `✕` после аудиции =
  rejected; версии считают попытки.
- manifest.json хранит per-part историю (v1 отклонён → v2 принят) — локально,
  без облака.
- Будущее (opt-in): «выжил ли слой в DAW через N сессий» — сравнение
  снапшотов сессии, чтобы отличить «оставил из вежливости» от «живёт в
  треке».

## 7. Технологический стек: egui vs web-панель

### 7.1 Сравнение

| Критерий | **egui (Rust), отдельное окно** | **Web-панель (локальный HTTP + браузер)** |
|---|---|---|
| Единство экосистемы | ✅ один язык с SoundCraft и audio-analyzer; общий словарь виджетов | ❌ второй-третий рантайм (JS + HTTP-мост) |
| Аудио-превью партий | ✅ cpal + лёгкий синт в процессе; низкая латентность; возможно переиспользовать MIT/Apache DSP-крейты SoundCraft | ⚠ WebAudio работает, но синхронный луп-старт с кнопками и логом — костыльнее; звук в другом процессе |
| Визуализация анализа (спектры, хромаграммы) | ⚠ базовые бары/heatmap рисуются руками; egui-plot есть, но это работа | ✅ canvas/D3 — лучшие графики почти даром |
| Чат/карточки | ✅ достаточно (текст, кнопки, chips) | ✅ тривиально, красивее |
| Реактивность на события шины | ✅ immediate mode — перерисовка из колбэков MCP без состояния | ⚠ нужен WS/SSE-пуш и state-менеджмент |
| «Code like water» (минимум зависимостей) | ✅ один бинарник, оффлайн, локально | ❌ node-сборка/версии браузера |
| Рабочий стол рядом с DAW | ✅ нативное окно, always-on-top, тайлинг, компактная полоса | ⚠ вкладка браузера/webview-обёртка |
| Скорость разработки UI | ⚠ медленнее на старте (графики, стили) | ✅ самая быстрая |
| Риск | 🎯 дрейф API pre-alpha SoundCraft — но он одинаков для обоих вариантов | 🎯 поддерживать два фронта (web + core) годами |

### 7.2 Рекомендация

**egui-приложение `l2t-cockpit` (Rust, отдельное окно).** Решающие аргументы:
(1) аудио-превью — сердце стейджинга, и оно должно быть мгновенным и
локальным; (2) одна экосистема с SoundCraft/audio-analyzer — общий язык,
общие крейты, общий тред в сообществе (волна 1 PRD = SoundCraft-комьюнити);
(3) UI — в основном карточки/гриды/лог, а не красивые графики; скромные
бары и heatmap egui осилит.

Web не выбрасываем, а **сужаем до ниши, где он сильнее**: **экспортируемый
статичный отчёт** (Loop Report / Self-Check отчёт как один HTML-файл в
workspace — шерить, архивировать, приложить к issues). Ноль рантайма, ноль
поддержки сервера. Полноценная веб-панель остаётся опцией, если появится
реальная потребность (удалённый доступ, планшет-пульт) — архитектура
«UI = проекция шины» это позволяет: cockpit-ядро (состояние+команды)
отделено от отрисовки.

Этапность (ориентир, без кода сейчас):
1. **Этап 1 — Cockpit MVP:** X-Ray-карточка + стейджинг-список с чипами и
   статусами (визуальный аудит, без звука) + лог шины. Уже закрывает
   «показать до импорта» на 70 %.
2. **Этап 2 — звук:** превью-движок (cpal + лёгкие синт/барабаны),
   mute/solo-аудиция, «прослушать в DAW» (карантин-полоса).
3. **Этап 3 — замыкание:** Self-Check-панель, accept-метрики в manifest,
   экспорт HTML-отчёта.
4. **Этап 4 — мозг:** визуализация автопилота qwen_bridge, воронка
   hero-сценария.

## 8. Риски и открытые вопросы

**Риски:**
1. **Два окна** (рассеивание внимания). Митигация: компактный режим-полоса
   (только статус+чат); типовой лэйаут «DAW слева, кокпит справа» как
   пресет; всё критичное дублируется кнопками в чате.
2. **Превью-синт ≠ финальный звук** (человек принял «не тот» бас).
   Митигация: двухступенчатая аудиция (§3.2), честная пометка «превью-тембр».
3. **egui-графики — трудозатраты.** Митигация: MVP-набор (бары, спарклайны);
   heatmap хромаграммы — позже; сложное — HTML-экспорт.
4. **Дрейф MCP-API SoundCraft (pre-alpha).** Митигация: кокпит говорит только
   словарём DawBackend, адаптер амортизирует.
5. **Acceptance Rate без пользователей** — жест есть, данных нет. Митигация:
   PRD уже имеет авто-прокси (voice motion, variety, вариативность); manifest
   готов к сбору с первых бета-тестеров волны 1.

**Открытые вопросы (для «Папы»):**
1. Согласиться ли с вариантом «отдельное окно» vs «панель-патч в
   SoundCraft» (я рекомендую окно; патч пересмотреть при интересе апстрима).
2. Формат manifest стейджинга (свой минимальный JSON vs переиспользовать
   что-то) — зафиксировать до этапа 1.
3. Превью-движок: минимальный собственный синт vs переиспользование
   DSP-крейтов SoundCraft (лицензии чисты, вопрос трудозатрат/декаплинга).
4. Приоритет HTML-отчёта (его можно сделать и до egui, польза для
   Self-Check видна сразу).
