## 0. Резюме (TL;DR)

**Рекомендуемый паттерн: «Кокпит над шиной» (Copilot Cockpit) — в терминах
VISION v2 это и есть AI-native wrapper.**

L2T не строит свою DAW и не прячется в чат. L2T — это **отдельное окно-
обёртка (Tauri + React) над MCP-мозгом, рядом с DAW**: три режима (**Loop
X-Ray → Стейджинг → Self-Check**), в которых пользователь работает с
музыкой, а ИИ проявляется невидимым помощником — карточками-предложениями и
«призрачными нотами» прямо на музыкальных объектах. Лог MCP-шины и чат
живут в свёртываемом инспекторе (прозрачность без чатоцентризма).

Границы (§3): кокпит = AI-кокпит в триаде FL — **Channel Rack** (наши
генераторы как каналы), **Piano Roll** (призрачные ноты предложений),
**Playlist read-only** до импорта; SoundCraft остаётся аудио-движком,
единственным редактором нот и микшером.

Ключевая идея, объединяющая всё предложение:

> **UI — это проекция MCP-шины.** Каждая кнопка = MCP-инструмент, каждый
> вызов агента = строка в инспекторе, каждое состояние = файл в workspace.
> Cockpit не имеет собственной скрытой логики — он визуализирует шину и
> файлы, а командовать может и человек (кнопками), и внешний агент (ZCode),
> и локальный «Мозг» (qwen_bridge). Это зеркальное отражение девиза
> SoundCraft «всё кликабельное — скриптуемо»: **всё скриптуемое — кликабельно**.

Связь с шиной (§6): Tauri IPC → Rust-ядро владеет stdio-клиентами серверов
(WebSocket не вводим). Железные правила (§10.2): никакого DSP в
UI-процессе — превью = проигрывание отрендеренного WAV; WebKitGTK-Linux
тестируем на первой неделе.

Формат нот: `suggestion.notes` = `core/midi_io` ({note, start, end,
velocity, channel}, тики) — единый контракт данных для UI-модуля (§5.1).

## 1. Исследование: чему учимся у существующих DAW

### 1.1 FL Studio — паттерн «слои + аранжировка» (обязательный разбор)

FL Studio построен вокруг триады **Channel Rack → Piano Roll → Playlist**:

- **Channel Rack** держит инструменты («каналы») и **step-секвенсор**: клетка
  = 16-я нота, клик = удар/нота. Паттерн длиной 1–512 шагов (1/16 — 64 такта
  в 4/4). Ключевая особенность: **паттерн — это данные всех каналов сразу**
  (степы + партии Piano Roll + автоматизация), а не одного инструмента.
- **Piano Roll** — лучший в индустрии редактор нот per-channel; в нём видны
  «призраки» (ghost channels) — бледные ноты других каналов для сведения
  гармонических слоёв.
- **Playlist** — аранжировка, где **паттерны ложатся как клипы** (Pattern
  Clips): каждый элемент (биты/бас/аккорды) — отдельный паттерн, паттерны
  стакаются на разных дорожках, такты собираются в песню. Picker Panel —
  библиотека паттернов с drag-and-drop.

**Что берём для L2T (это ДНК нашего кокпита, §3–§4):**
1. **Партия = короткий переиспользуемый паттерн-слой** — ровно так работают
   наши midi-gen генераторы (1-тактовые бас-паттерны, 4-тактовые прогрессии,
   барабанные лупы с филлами). Буквально по VISION v2: **3 генератора
   midi-gen = 3 канала Channel Rack**.
2. **Ghost channels → «призрачные ноты» L2T**: FL показывает чужие ноты
   бледным слоем в своём редакторе — мы показываем сгенерированные партии
   слоем-предложением поверх лупа, до accept. VISION v2 доводит метафору до
   контракта данных (§5).
3. **Просмотр слоя без открытия редактора** (мини-превью нот прямо в стойке)
   — пользователь видит, что ему предложили, не покидая кокпит.
4. **Слоистая аудиция**: mute/solo на слой — комбинируем «луп + бас + аккорды»
   на слух до любого импорта.
5. **Паттерн → аранжировка как отдельный шаг**: у нас = «заполнить N тактов»
   (рецепт `duplicate_extend`, правило 6 шины) и раскладка в DAW — FL-шный
   переход Channel Rack → Playlist.

**Что НЕ берём:** «паттерн содержит все инструменты сразу» — нам нужна
обратная семантика (партия = отдельный MIDI-файл = отдельный слой =
отдельная дорожка в DAW), потому что наша ценность — редактируемость каждой
партии по отдельности.

### 1.2 Ableton Live — клип-парадигма (Session View)

Session View: колонки = треки, строки = сцены; клипы запускаются синхронно
глобальному темпу (launch quantization), сцена = комбинация слоёв одним
нажатием, Follow Actions автоматизируют переходы, джем в Session
записывается в линейный Arrangement.

**Что берём:**
1. **Аудиция по клипам до коммита**: сгенерированная партия = «клип в
   холдиг-арее», который запускается в синхронном лупе — как клип Session
   View, но ещё не в проекте. Это главный механизм «показать ДО импорта».
2. **Комбинации слоёв = сцены**: кнопка «▶ всё вместе» и пресеты комбинаций
   (луп+бас / луп+бас+аккорды+бит) — сценический способ сравнить варианты.
3. **Черновик → финал как два режима**: стейджинг (нелинейный джем с
   генератором) → импорт в DAW (линейная аранжировка). Мост «Record to
   Arrangement» у нас = кнопка «Импорт принятых».

**Что НЕ берём:** Session View как основную форму главного окна — наш
линейный аранжировщик уже есть (SoundCraft), дублировать его не нужно.

### 1.3 Bitwig Studio — модульность и The Grid

Bitwig: Poly Grid / FX Grid / Note Grid (160+ модулей), модуляторы вешаются
почти на любой параметр, сигналы Grid взаимодействуют с DAW-уровнем —
философия «всё модульно, всё модулируемо». Note Grid примечателен: **ноты —
это тоже патчуемые данные**.

**Что берём (на уровне философии, не UI):**
1. **Компонуемость = наша MCP-шина.** «Всё модульно» у нас уже есть: уши
   (audio-analyzer), руки (midi-gen), тело (DAW), мозг (qwen_bridge). Задача
   UI — **показать композицию явно**: инспектор шины делает модульность
   видимой (как патч-корды Grid видны на экране).
2. **Note Grid-настройка**: партия как данные (MIDI-файл + JSON-параметры),
   которые можно пере-параметризовать (style/voicing/variation) — наши
   chips-регенерации (§7.1) — это «патчинг нот».

**Что НЕ берём:** визуальный патчинг как форму интерфейса — для целевой
аудитории (продюсеры, не модульные синтезаторы) это лишний слой абстракции.

### 1.4 SoundCraft — наш хост

SoundCraft (storytold/soundcraft): чистый Rust, egui (`soundcraft-ui-egui`,
слоистая архитектура — «ниже UI ничего не знает про egui», GUI заменяем),
Pro Tools-подобные окна Edit/Mix, MIDI-редактор, перемещаемые/докуемые
панели, 120 fps при ~70 треках. Главное для нас: **каждое кликабельное
действие = команда с JSON-параметрами** (CLI, JSON-канал, **MCP-сервер**),
headless-режим, скриншоты, `session.inspect` для самопроверки агента.
Лицензия MIT/Apache-2.0 (форки обязаны убрать товарные знаки). Статус
pre-alpha (~40 % пути), т.е. API будет дрейфовать — учтено в §6/§10/§11.

**Что берём:** SoundCraft остаётся **аудио-движком, единственным редактором
нот и микшером** — после accept вся правка живёт там, микс-UI не дублируем
(VISION v2: SoundCraft-UI остаётся открытым как микшер). Cockpit не
конкурирует с DAW, а готовит материал для неё. Плюс «всё кликабельное —
скриптуемо» зеркалим в «всё скриптуемое — кликабельно».

### 1.5 MAGDA — референс AI-нативной DAW

MAGDA (Conceptual-Machines/magda-core, magda.land): «Multi-Agent Digital
Audio Workstation», C++23/JUCE, GPL-3.0, активная разработка с января 2026.
Как они встроили AI в UI:

- **AI-чат панель** слева (рядом с Inspector); справа браузеры; снизу
  контекстный редактор; три вида — Arrangement / Session / Mix.
- Агенты работают по схеме **«чат → LLM генерирует DSL → DAW исполняет DSL
  прямо в проекте»**; DSL видим пользователю. BYOAK (свои API-ключи) или
  локальный llama.cpp.
- Агенты **читают сессию и действуют** через DSL: промпт-в-паттерн в
  MIDI-секвенсоре, агент сведения («измерь микс и ответь по цифрам»),
  similarity-поиск в медиатеке, автоматизация по запросу.
- **MCP endpoint + WebSocket + OSC** — внешние AI-хосты могут рулить MAGDA.

**Что берём (главные уроки):**
1. **Команды агента видимы и инспектируемы** (их DSL) — у нас эту роль играет
   инспектор MCP-вызовов. Никаких невидимых мутаций проекта.
2. **Агент видит состояние сессии перед действием** — наш pull-принцип
   (`get_session` перед действием) уже в DawBackend.
3. **MCP-endpoint для внешних хостов** — мы и есть MCP-native, кокпит лишь
   не должен прятать шину за собой.

**Чего избегаем (дважды):** во-первых, MAGDA — это **целая DAW** (GPLv3,
свой движок, свой UI); мы строим **агентный слой над существующей DAW**.
Во-вторых, чат у MAGDA — центр интерфейса; VISION v2 прямо предписывает
обратное («уходим от чата»): наш центр — музыкальные панели, а невидимый
помощник проявляется карточками на объектах. Чат остаётся в инспекторе как
режим power-user.

## 2. Рекомендуемый UI-паттерн: «Кокпит над шиной»

### 2.1 Почему не альтернативные формы

Рассмотрены три формы верхнего уровня:

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **(а) Панель внутри SoundCraft** (оверлей-патч) | Один процесс, нативный док | Привязка к одному хосту (против философии DawBackend); патч расходится с апстримом; UI-слой SoundCraft — чужая территория, которую мы обещали не форкать; Tauri-стек VISION v2 сюда не встраивается | ❌ |
| **(б) Отдельное окно-«кокпит» над MCP** (Tauri-обёртка) | Хост-агностик; нулевое вмешательство в DAW; шина видима целиком; работает даже без DAW (анализ+генерация); стек VISION v2 ложится ровно | Два окна на экране | ✅ **рекомендовано (= AI-native wrapper VISION v2)** |
| **(в) Только чат/терминал (статус-кво)** | Уже работает; агент-нативным юзерам хватает | Нет аудиции до импорта, нет визуализации анализа, высокий порог для «волны 2+»; Acceptance Rate нечем измерять жестом; против «уходим от чата» | ✅ остаётся как режим power-user |

Вариант (б) не отменяет (в): **кокпит — это проекция того же самого**, что
можно делать из чата. Ничего эксклюзивного для GUI не создаётся.

### 2.2 Пять принципов кокпита

1. **Кнопка = MCP-инструмент.** Каждый элемент UI вызывает тот же
   инструмент, что доступен агенту из чата/CLI. Обратное тоже верно: всё,
   что агент может сделать, имеет кнопку. Нет скрытых возможностей.
2. **Инспектор шины = истина.** Свёртываемый drawer с живым логом всех
   MCP-вызовов (команда, параметры, статус, время). Это «инспектор DSL» в
   духе MAGDA и гарантия прозрачности из PRD — но не центр композиции.
3. **Превью ≠ коммит.** Ничто не попадает в DAW-сессию без явного accept.
   До accept партия живёт как **призрачная нота** — данные в UI-слое;
   SoundCraft-сессия = единственный источник истины, второго редактора нет.
4. **Workspace = состояние.** Стейджинг персистится файлами в workspace
   (.mid + WAV-превью + manifest.json с версиями, статусами, rationale
   предложений). Перезапустил кокпит — увидел то же самое. Нет скрытой БД
   состояния UI (правило 1 шины).
5. **Никакого DSP в UI-процессе** (железное правило VISION v2). UI —
   control-plane: аудио в кокпите = только **проигрывание отрендеренных
   WAV**; весь синтез — на стороне генерации/DAW (§4.2, §10.2).

### 2.3 Общая схема

```
 рабочее место музыканта (один экран, окна рядом или тайлинг)
┌──────────────────────────────────┐  ┌──────────────────────────────────┐
│  SoundCraft (или др. DawBackend) │  │  L2T Cockpit (Tauri + React)     │
│  ═══ аудио-движок, редактор,     │  │  ═══ AI-обёртка над шиной ═══    │
│      микшер (§3) ═══             │  │                                  │
│  timeline / клипы / ноты         │  │  [Loop X-Ray][Стейджинг][Check] │
│  фейдеры, плагины, автоматизация │  │  ┌────────────────────────────┐  │
│  ──────────────                  │  │  │ панель режима (§4)         │  │
│  сюда прилетают ПРИНЯТЫЕ партии  │  │  │ музыкальные объекты +      │  │
│  (MIDI-дорожки, редактируемые);  │  │  │ призрачные ноты агента     │  │
│  остаётся открытым как микшер    │  │  └────────────────────────────┘  │
│                                  │  │  ▤ инспектор шины (лог+чат,     │
│                                  │  │    свёрнут; §4.4)               │
└───────────────▲──────────────────┘  └───────────────┬──────────────────┘
                │      DawBackend: import_midi,        │  Tauri IPC →
                │      get_session, set_tempo, render  │  Rust-ядро владеет
                └────────────── MCP-шина (stdio) ──────┘  MCP-клиентами (§6)
                        audio-analyzer · midi-gen · (qwen_bridge)
                     данные (WAV/MIDI/JSON) ходят через workspace
```

Кто «держит штурвал», кокпиту безразлично: нажатие кнопки (человек),
запрос из внешнего агента (ZCode), локальный мозг (qwen_bridge) — в логе
виден только эмитент команды (§6, §7.2).

## 3. Границы UI: кокпит и хост

Раздел фиксирует разделение труда двух приложений (уточнение спеки, п. 2).
Ось этой границы — **между приложениями**; вторая ось (человек ↔ агент) —
в §8. Формула: **кокпит готовит и предлагает, хост звучит и хранит**.

### 3.1 Триада FL, воплощённая в кокпите

AI-кокпит буквально повторяет триаду FL Studio, но каждая часть меняет
семантику под нашего агента:

| Часть FL | В L2T Cockpit | Семантика |
|---|---|---|
| **Channel Rack** | **Стейджинг: генераторы = каналы.** Канал «🎸 bass», канал «🎹 chords», канал «🥁 drums» — это инструменты `midi-gen.generate_bassline/chord_progression/drum_pattern`. Новый канал = новый MCP-инструмент (будущие: мелодия, арпеджиатор). Канал = ряд-карточка слоя (§4.2) |
| **Piano Roll** | **Piano Roll с призрачными нотами.** Просмотр предложения нотами из контракта `suggestion.notes[]` (§5.1 — единый формат `core/midi_io`: `{note, start, end, velocity, channel}`, тики): партия рисуется бледным слоем поверх референса (луп/другие слои), наложение слоёв. v0 минимальный (решение мейнтейнера): zoom, без velocity-lane; **read-only**: правка нот живёт ТОЛЬКО в SoundCraft после accept («никаких двух редакторов») |
| **Playlist** | **Read-only проекция таймлайна.** Кокпит показывает сессию хоста (из `daw.get_session`) как контекст: где окажутся импортированные партии, где маркеры, граница существующей аранжировки. Никакого drag&drop/редактирования — до «Импорт принятых», который материализует партии дорожками хоста (v1+ добавляет аранжировочные интенты, §10.3) |

```
┌─ L2T Cockpit (Tauri+React) ──────────┐    ┌─ SoundCraft (хост) ─────────────┐
│ Channel Rack:  генераторы = каналы   │    │ аудио-движок (рендер, синтез)   │
│ Piano Roll:    призрачные ноты       │───▶│ редактор нот (единственный)     │
│ Playlist:      read-only проекция    │    │ аранжировка/структура           │
│ Self-Check, инспектор шины           │    │ МИКСЕР: фейдеры/пан/плагины     │
└───────────────────────────────────────┘    └─────────────────────────────────┘
     accept ──▶ daw.import_midi ──▶ призрачная партия материализуется дорожкой
```

### 3.2 Матрица ответственности

| Область | L2T Cockpit | SoundCraft (хост) |
|---|---|---|
| Анализ лупа и его показ | ✅ Loop X-Ray (§4.1) | — |
| Генерация / регенерация / версии | ✅ через midi-gen | — |
| Быстрая аудиция (превью WAV) | ✅ HTML-audio, слои, сцены | — |
| Accept / reject предложений | ✅ жест человека (§5) | — |
| WYSIWYG-прогон тембра | инициирует (карантинная полоса) | ✅ звучит, undo |
| Импорт MIDI | инициирует | ✅ исполняет (`import_midi`, инструменты) |
| **Правка нот** | ❌ никогда (read-only piano roll) | ✅ **единственный редактор** |
| **Аранжировка** (структура, дубли) | read-only проекция (v1: интенты) | ✅ правка здесь |
| **Микс** (фейдеры, пан, плагины, sends) | ❌ **ни одного фейдера в кокпите** | ✅ остаётся открытым как микшер |
| Render / bounce | инициирует, читает отчёт | ✅ рендерит (LUFS и т.п.) |
| Темп/тональность сессии | предлагает (adopt, opt-in) | ✅ источник истины |

### 3.3 Правило единого источника истины (anti-dual-source)

Граница перехода — это жест accept:

- **До accept**: партия существует только в UI-слое кокпита и файлах
  workspace (.mid/WAV/manifest) — для SoundCraft её нет.
- **После accept**: партия существует только в сессии хоста — кокпит держит
  лишь read-only статус («принято, дорожка 7»). Редактировать принятую
  партию из кокпита нельзя; регенерация после accept = новое предложение
  (новая призрачная версия) с повторным accept.
- Переход атомарен и логируется в manifest (§5) — этим снимается риск
  «dual source of truth» из VISION v2.

## 4. Панели и режимы

Три режима сверху + свёртываемый инспектор. Режимы — это воронка
hero-сценария из PRD: **понять луп → послушать варианты → проверить**.

### 4.1 Loop X-Ray (анализ лупа)

Первая остановка: «брось луп — узнай, что это». Карточка-отчёт поверх
реального выхода audio-analyzer (числа — из наших проверенных прогонов):

```
┌─ Loop X-Ray ──────────────────────────────────────────────────────┐
│  📥  перетащи WAV/FLAC сюда            [переанализировать]        │
│ ───────────────────────────────────────────────────────────────── │
│  loop.wav · 32.0 s · 44.1 kHz · mono                               │
│                                                                    │
│  TEMPO       60.1 BPM   уверенность ▓▓▓▓░░ 64%   (альтернатива:    │
│                        120.2 — возможно ×2 по хэтам [выбрать 120])│
│  KEY         A minor   уверенность ▓▓▓▓▓░ 91%  ≡ C major (отн.)   │
│  LOUDNESS    −12.0 LUFS · TP −2.4 dBTP                             │
│              цель: [Spotify −14 ▾]  до цели: +2.0 dB              │
│                                                                    │
│  СПЕКТР (что не так):  суб-бас ▁ низкие ▃ средние ▂ верх ▁        │
│  → «лупу не хватает низа и воздуха» [+] бас [+] воздух  ← карточки │
│                                                                    │
│  РИТМ       onset-плотность 2.1/долю → рекомендация: hat 8-е,     │
│             прямая бочка; свинг 0%                                │
│ ───────────────────────────────────────────────────────────────── │
│  [✓ Применить к сессии: 60 BPM + key-маркер Am]   ← opt-in, #1702 │
│  [→ В стейджинг: сгенерировать партии]                            │
└────────────────────────────────────────────────────────────────────┘
```

Дизайн-решения:
- **Уверенность — гражданин первого класса.** Урок PoC: значения с низкой
  уверенностью нужно интерпретировать, а не цитировать. Всё ниже ~70 %
  рисуется приглушённо + человеческая интерпретация.
- **×2-темп — это фича панели, а не бага анализатора**: обе гипотезы (60/120
  от hat onset-lock — реальный случай из наших тестов) показываются
  рядом, выбор за человеком.
- **Relative-key эквивалентность видна сразу** (A minor ≡ C major) — правило
  7 шины, отлитое в `keys_match`, здесь просто визуализируется.
- **Спектр → действие**: провал в полосе сразу даёт карточку-кнопку
  «[+] бас» (переход в стейджинг с предзаполненной генерацией). Это мост в
  §4.2 — ИИ-помощник, не чат: предложение живёт на данных.
- **Adopt Loop Settings = явный диалог**, не автоприменение (правило 4:
  сессия — источник истины; opt-in половина issue #1702).
- Полоса секций (intro/drop/…) появится, когда апстрим починит panic в
  sections.rs (наш issue #3 у JuzzyDee).

### 4.2 Стейджинг (сердце интерфейса)

«Channel Rack для сгенерированного» (FL) + «клипы до коммита» (Ableton) +
«призрачные ноты до accept» (VISION v2). Каждая партия — **слой-карточка**
(канал): мини-превью нот (единый формат §5.1), параметры генерации как
chips, версия, кнопки аудиции/регенерации/приёмки. Контракт данных
предложения — §5.1.

```
┌─ Стейджинг · loop.wav 60 BPM A minor ──────────────────────────────┐
│ СЛОИ = КАНАЛЫ (луп всегда внизу как референс)                      │
│ ┌────────────────────────────────────────────────────────────────┐ │
│ │ 🎸 bass      v2  ▶ ─●──●──●──●──●─  [style: syncopated ×]      │ │
│ │   призрачно поверх лупа · 5 нот · off-beats 1.5s/3.5s          │ │
│ │   «синкопа в духе ритма лупа (onset 2.1/долю)»  [↻] [✓] [✕]    │ │
│ │   история: v1 basic → v2 syncopated            ⏳новое          │ │
│ ├────────────────────────────────────────────────────────────────┤ │
│ │ 🎹 chords   v1  ▶ ─▬▬──▬▬──▬▬──▬▬─  [voicing: voiceled ×]      │ │
│ │   Am/C · F/C · C · G/D · движение 4            [↻] [✓] [✕]     │ │
│ │   «инверсии: соседние аккорды ≤4 п/т (block=7)» ⏳ прослушано   │ │
│ ├────────────────────────────────────────────────────────────────┤ │
│ │ 🥁 drums    v1  ▶ ─●●●●●●●●●●●●─  [style: basic][fill: 4-й такт]│ │
│ │   kick 1&3 · snare 2&4 · hats 8-е              [↻] [✓] [✕]     │ │
│ └────────────────────────────────────────────────────────────────┘ │
│ 🎵 loop.wav (источник)  ▶ ─▬▬▬▬▬▬▬▬▬▬▬▬─  🔒 референс, не трогаем  │
│ ────────────────────────────────────────────────────────────────── │
│ СЦЕНЫ:  [луп+бас] [луп+бас+аккорды] [всё] [▶ прослушать выбранное]  │
│ [▤ Piano Roll: призрачный просмотр выбранных слоёв]                 │
│                                                                    │
│ [⤓ Импорт принятых →]   (v0: Playlist read-only; «заполнить 8 тактов»│
│                          — v1-интент, §10.3)                       │
└────────────────────────────────────────────────────────────────────┘
```

Дизайн-решения:
- **Призрачные ноты**: партии рисуются бледным слоем «поверх лупа»
  (FL ghost channels) — на мини-превью карточки и в Piano-roll-просмотре
  (наложение выбранных слоёв; v0 минимальный: zoom, без velocity-lane —
  решение мейнтейнера). Rationale из контракта (§5.1) — подпись под карточкой:
  ИИ объясняет себя в одну строку, не диалогом.
- **Статусы аудита на карточке** — сырьё Acceptance Rate (§5.3): `⏳
  сгенерировано → ◀ прослушано → ✓ принято / ✕ отклонено`. История версий
  сохраняется (v1 не удаляется регенерацией; «принять v1 после
  прослушивания v3» — реальный сценарий).
- **Chips = реальные параметры midi-gen** (`style`, `voicing`, `variation`,
  `bars`). Клик по chip = регенерация с другим значением; menu chip =
  выпадающий список. Кнопка = MCP-вызов `midi-gen.generate_*`.
- **Аудиция без DSP в UI (железное правило)**: превью = **проигрывание
  отрендеренного WAV**. Рендер делает конвейер вне UI-процесса: midi-gen
  отдаёт .mid → **сайдкар GM-синт** рендерит WAV (решение мейнтейнера, §10.2) →
  UI проигрывает файл (HTML audio) синхронно темпу, слоями, mute/solo на
  лету. Луп крутится, призрачные партии включаются кнопкой.
- **Двухступенчатая аудиция** (честно про звук):
  1. *быстрая* — WAV-превью сайдкар-синта (мгновенно для итераций
     регенерации; прямой импорт в SoundCraft шёл по ~10 с — слишком долго
     для перебора вариантов);
  2. *WYSIWYG* — «прослушать в DAW»: агент импортирует в карантинную
     staging-группу треков (muted, вне аранжировки), где звучат настоящие
     `subtractive_synth`/`drum_synth`. Не понравилось — undo.
- **«Импорт принятых»** — единственная кнопка, меняющая DAW-сессию: для
  каждого ✓-слоя `daw.import_midi` + инструмент назначается хостом
  (SoundCraft делает это сам). Призрачные ноты «материализуются» в
  редактируемые MIDI-дорожки — с этого момента ноты принадлежат человеку
  (PRD: «вы владеете каждой нотой»), правка — только в SoundCraft. Тот же
  .mid, что слушали в превью, читает `midi_io` (§5.1) и импортирует хост —
  превью и результат в DAW видят одни и те же ноты.
- **«Заполнить N тактов»** (v1): длительность выбирается намерением («8
  тактов»), кокпит прячет экспоненциальный `duplicate_extend` за интентом
  (правило 6). В v0 отсутствует — аранжировку не редактируем.

### 4.3 Self-Check (проверка результата)

Появляется после bounce. A/B-отчёт «луп → микс» на реальных числах нашего
полного теста:

```
┌─ Self-Check ───────────────────────────────────────────────────────┐
│  bounce_v3_full.wav · 32.0 s · −21.2 LUFS · peak −6.8 dB           │
│ ─────────────────────────────────────────────────────────────────  │
│  ПОКАЗАТЕЛЬ      ЛУП          МИС         ВЕРДИКТ                  │
│  Тональность     A minor      A minor 0.84  ✓ (≡ C major — отн.)   │
│  Темп            60.1         60.1          ✓                       │
│  Громкость       −12.0 LUFS   −21.2 LUFS    ⚠ до Spotify −14:      │
│                                             +7.3 dB [normalize]    │
│ ─────────────────────────────────────────────────────────────────  │
│  ЧТО ДОБАВИЛИ СЛОИ (Δ по полосам):                                 │
│  суб-бас +5.7 · низкие +6.7 · средние +6.5 · верх +2.1 dB           │
│  → «слои заполнили ровно те полосы, которых лупу не хватало» ✓     │
│  (план из Loop X-Ray выполнен)                                     │
│ ─────────────────────────────────────────────────────────────────  │
│  ИТОГ: ✅ сходится · трек готов к сведению/мастерингу              │
│  [normalize до цели] [→ досдать в DAW] [отчёт .html в workspace]   │
└─────────────────────────────────────────────────────────────────────┘
```

Дизайн-решения:
- **Verdict — трёхцветный, но с толкованием**: ✓ / ⚠ (относительная
  тональность, ×2-темп, громкость до цели) / ✗ рассинхрон. Правило 7
  (relative-key + перепроверка тональности ПОСЛЕ аранжировки) —
  пользовательская формулировка, зашитая в UI: чек выполняется по кнопке
  «Проверить микс», т.е. всегда после завершения аранжировки.
- **Самопроверка агента ≠ решение агента**: вердикт — данные для человека.
  «Трек готов к мастерингу» — фраза ассистента, кнопки — у человека.
- **Замкнутость контура наглядна**: панель показывает Δ полос против
  «диагноза» из X-Ray — «план → исполнение» одним взглядом. Это
  визуализация реального инструмента `mcp__audio-analyzer__compare`.
- **Экспорт отчёта** — статичный HTML в workspace (шеринг/архив; ниша, где
  web-техника непобедима, §10).

### 4.4 Инспектор шины и чат (drawer, свёрнут по умолчанию)

VISION v2: «уходим от чата — пользователь работает с музыкой, ИИ невидимый
помощник». Поэтому лог и чат — не колонка интерфейса, а **выдвижной
инспектор** (▤, правый край), раскрываемый по желанию и в режимах
«Агент»/«Автопилот» (§7.2):

```
┌─ Инспектор шины (drawer) ────────────┐
│ ┌───────────────────────────────────┐ │
│ │ [ты]  сделай бас синкопированным  │ │ ← чат: режим power-user
│ │ [L2T] midi-gen.generate_bassline  │ │
│ │        {key:"Am", style:"syncop…) │ │ ← команды видимы
│ │        → bass_v2.mid · 0.3 s ✓    │ │   (урок MAGDA: DSL инспектируем)
│ │ [L2T] обновил слой «bass» до v2 — │ │
│ │       карточка в Стейджинге       │ │ ← ответ = действие на панели,
│ └───────────────────────────────────┘ │   не текст в чате
│ ─ лог шины ────────────────────────── │
│ 12:01:03 soundcraft.get_session ✓ 40ms│
│ 12:01:04 midi-gen.bassline …     ✓0.3s│
│ 12:01:31 soundcraft.import_midi  ⏱30s │
│           → inspect: трек 7, 4 ноты ✓│
│ ──────────────────────────────────── │
│ [ввод…                          ] ⏎  │
└───────────────────────────────────────┘
```

- Верх — **чат** (для power-users и агента), низ — **лог** (машине).
  Ответ агента на запрос из чата — не текстовое сообщение, а **действие на
  панели** (обновлённая карточка + toast «слой bass → v2»): ИИ невидим, его
  работа видна в музыке.
- **Таймаут ≠ отказ — видно глазами** (правило 2): строка лога меняет
  статус ⏱ → авто-`inspect` → ✓, а не молчаливый ретрай.
- Прозрачность сохранена полностью: лог пишет всё, даже свёрнутый.

### 4.5 Панели кокпита в терминах компонентов и состояний

Мост спеки к реализации (сессия UI-модуля, этап 1). Это **не код**:
имена компонентов и состояний — словарь для согласования с
`docs/ipc-contract.md` v0.1 (TS-зеркало — `ui/src/types/contract.ts`).
Что не названо здесь — решает UI-модуль; расхождение словаря с
контрактом = баг на ревью.

**Единый формат нот — контракт (не договорённость).** Все компоненты,
рисующие ноты (`GhostPreview`, `PianoRollView`, будущие), потребляют
`suggestion.notes[]` только в формате midi_io: `{note, start, end,
velocity, channel}` в тиках; перевод тиков в доли/секунды — по конверту
(`ticks_per_beat`, `bpm`) из `core/midi_io.load_notes` (§5.1). Никаких
`pitch`/`len`/локальных альтернативных структур (правило 3
ipc-contract v0.1).

**Карта компонентов (v0):**

```
<App>                                 состояние = проекция шины (§6), не владелец данных
├─ <TopBar/>                          сессия · BPM · key · транспорт ← get_bus_state
├─ <XRayPanel/>                       §4.1
│  ├─ <ConfidenceRow metric/>         TEMPO/KEY/LOUDNESS; conf < ~70% → приглушить + альтернатива
│  ├─ <SpectrumBars/>                 полосы + карточки-действия «[+] бас» (§4.1)
│  └─ <AdoptDialog/>                  «Применить к сессии» — единственная opt-in модальность
├─ <StagingPanel/>                    §4.2 = Channel Rack
│  ├─ <SourceLoopCard/>               🔒 референс-канал лупа
│  ├─ <PartChannel part/> ×3          bass | chords | drums (3 генератора midi-gen)
│  │  ├─ <GhostPreview/>              мини-превью нот (midi_io) + rationale-строка
│  │  ├─ <ParamChips/>                style/voicing/variation/bars → regenerate(params_diff)
│  │  ├─ <VersionHistory/>            v1→v2… (история не удаляется, §5.2)
│  │  └─ <SuggestionActions/>         [↻] [✓] [✕] — жесты аудиции/accept/reject
│  ├─ <PianoRollView/>                наложение призрачных слоёв; v0: zoom, без velocity-lane
│  ├─ <ScenesBar/>                    mute/solo-комбинации для превью-аудиции
│  └─ <ImportAcceptedButton/>         единственный мутатор DAW-сессии
├─ <SelfCheckPanel/>                  §4.3 светофор
│  └─ <VerdictRow metric/>            ✓ / ⚠ + фикс-кнопка / ✗
└─ <BusInspector/> (drawer)           §4.4: лог шины + чат power-user
```

**Машина состояний канала партии (`PartChannel`):**

```
idle ──generate──► generating ──suggestion_updated──► generated
                                                        │ ▶ (аудиция превью)
                 regenerate(params_diff)                ▼
                   ┌───────────────────────────────► auditioned
                   │                                    │
                   │                      accept_part / reject_part
                   ▼                                    ▼
              v(N+1) generated                    accepted | rejected
```

- Статусы = словарь контракта (`generated → auditioned → accepted |
  rejected`, ipc-contract.md §Данные). React-состояние — **зеркало
  событий ядра** (`suggestion_updated`), не владелец: после перезапуска
  кокпита состояние восстанавливается из manifest.json (§2.2, принцип 4).
- Жесты accept/reject — только через команды ядра (`accept_part` /
  `reject_part`), оптимистично: локально перевести статус сразу, при
  ошибке — откат + toast (правило 3 шины: ошибка видима, не спиннер).
- Генерация **не** оптимистична: канал в `generating` ждёт
  `suggestion_updated`, трёхуровневая индикация — ниже.

**Призрачный слой (`GhostLayer` — общий паттерн для `GhostPreview` и
`PianoRollView`):**
- Рендер поверх референса бледным слоем; цвет закреплён за каналом
  (консистентная палитра bass/chords/drums между мини-превью и
  PianoRollView).
- Появление — «вплывание»: трёхуровневая AI-индикация (USER FLOW v1,
  черновик в памяти): <300 мс — без индикации; 0.3–10 с — канал «дышит»
  (пульс на кнопке), призрак вплывает; >10 с — строка AI Dock
  `● ИИ: [tool] — действие… [отменить]`, `source_tool` всегда виден.
  Никогда не модальные спиннеры.
- Interaction v0: hover на карточке = rationale + confidence; ноты не
  кликабельны (read-only — правка только в SoundCraft после accept, §3.1).
- База — piano-roll из audio-ui (copy-in, MIT, находка OSS-разведки):
  расширяется ghost-слоем без форка; эскалация рендера DOM→konva→pixi —
  только по профилированию (до того отсечена, собрание №1).

**Светофор Self-Check:** `verdict` из `run_self_check` маппится в три
состояния — **ok** (зелёный), **warn** (жёлтый + кнопка-фикс: normalize
до цели / пере-проверка после аранжировки), **fail** (красный + паттерн
«починить за меня» из USER FLOW v1). Панель никогда не блокирует UI.

**Правила-ограничители (не забыть в реализации):**
1. Ни одного микс-контрола/фейдера в v0 (§3.2) — микшер живёт в SoundCraft.
2. Playlist-зона — read-only проекция `get_bus_state` (§3.1), без drag&drop.
3. Ошибки шины = toast с текстом JSON-RPC error; таймаут ядро превращает в
   inspect-вердикт (§6.2) — UI показывает `⏱ → inspect → ✓/✗`.
4. Все типы на проводе — из `ui/src/types/contract.ts` (зеркало
   ipc-contract.md); локальные интерфейсы не создают альтернативных
   форматов нот.

## 5. Призрачные ноты — контракт данных и Acceptance Rate

### 5.1 Контракт suggestion

«Призрачные ноты» — не фича UI, а **контракт данных** (VISION v2). Любое
предложение партии — неважно, откуда оно пришло (кнопка человека,
midi-gen-канал, внешний агент ZCode, локальный мозг qwen_bridge) —
существует как экземпляр одного контракта:

```
suggestion = {
  notes:        [{note, start, end, velocity, channel}, ...], // тики от начала клипа
  rationale:    "синкопа на 1.5/3.5 с, корень Am", // одна строка человеку
  confidence:   0.0..1.0,                          // от генератора/агента
  source_tool:  "midi-gen.generate_bassline v3",   // происхождение
  params:       {key, style, bars, embed_tempo}    // что регенерация меняет
}
// notes = в точности формат core/midi_io.load_notes (§5.1):
//   абсолютные тики; ticks_per_beat — в конверте load_notes
//   (у midi-gen 480) — по нему тики переводятся в доли/секунды (bpm там же);
//   channel 0-indexed, ударные = 9; форшлаг-ретриггеры раскрыты стеком
//   midi_io; сортировка (start, note)
```

Требования к контракту:
- **source_tool обязателен** — происхождение каждого предложения видно
  (прозрачность PRD: «никаких скрытых API»); в UI он мелким шрифтом на
  карточке и в инспекторе.
- **rationale рендерится** на карточке слоя — ИИ объясняется одной строкой,
  не диалогом.
- **params — это в точности параметры MCP-инструмента**: регенерация из UI
  = тот же вызов с другими params (§7.1). Не существует «UI-специфичных»
  параметров.
- notes — **в точности формат `core/midi_io.load_notes`** (унификация v0.4,
  решение собрания №1): `{note, start, end, velocity, channel}`, абсолютные
  тики от начала клипа, channel 0-indexed (ударные = 9), форшлаг-ретриггеры
  раскрыты стеком midi_io, сортировка (start, note); `ticks_per_beat` и
  `bpm` для перевода тиков в доли/секунды берутся из конверта `load_notes`.
  Единый формат всех нот в проекте: midi-gen пишет .mid → midi_io читает →
  контракт отдаёт UI для отрисовки (§3.1, §4.2) → тот же .mid
  импортирует хост. Один формат — один источник правды; после accept партия
  материализуется дорожкой хоста.
- Смежный документ: полный конверт предложения на проводе (`version`,
  `part`, `status`) и все команды/events UI↔ядро определены в
  `docs/ipc-contract.md` (v0.1, правило №7) — этот proposal фиксирует
  семантику, контракт — типы для Rust/TS-сторон. Схема notes в обоих
  документах едина (v0.4).

### 5.2 Жизненный цикл предложения

```
generated ──▶ auditioned ──▶ accepted  (→ материализация в хосте, §3.3)
    │                          ▲
    │ regenerate (params diff) │
    ▼                          │
  v2, v3 … ────────────────────┘
    │
    └──────────────────▶ rejected (версия остаётся в истории)
```

- Каждая версия — отдельный экземпляр контракта; история не удаляется
  («принять v1 после прослушивания v3» — реальный сценарий).
- До accept предложение живёт только в UI-слое и workspace (manifest);
  SoundCraft-сессию не трогает — **никаких двух редакторов**.

### 5.3 Инструментация Acceptance Rate (PRD §4)

Метрика PRD («процент сгенерированных партий, которые пользователь оставил
в аранжировке») рождается как **честный жест в стейджинге**, а не
телеметрия-шпионаж:

- **Событие** = строка в manifest.json (локально, без облака):
  `{ts, part, version, params, source_tool, decision: accepted|rejected,
    mode: manual|agent|autopilot, audition_count}`.
  Схема события = поля контракта suggestion (§5.1: version, params,
  source_tool) **за основу** + решение/контекст — единый словарь с §5.1
  (решение мейнтейнера, собрание №1).
- **accept** = кнопка «✓ Принять» (или «Импорт принятых» без отклонения);
  **reject** = «✕» после аудиции; версии считают попытки:
  `acceptance_rate(part) = accepted_versions / total_versions`.
- `mode` различает, кто инициировал (человек кликом / агент из чата /
  автопилот) — для будущих исследований «когда ИИ угадывает».
- Связка с авто-прокси PRD (voice motion, variety, вариативность ударных):
  прокси считают генераторы, жесты считает UI — обе ленты сходятся в
  manifest и сравниваются по `params`.
- Будущее (opt-in): «выжил ли слой в DAW через N сессий» — сравнение
  снапшотов сессии, чтобы отличить «оставил из вежливости» от «живёт в
  треке».
- day-one: контракту подчиняются все предложения с первой версии кокпита —
  метрика собирается с первого дня (требование VISION v2).

## 6. Связь с MCP

### 6.1 Топология

```
┌─ React (front) ────────┐  Tauri IPC    ┌─ Rust-ядро (Tauri main) ──────┐
│ панели, карточки,      │◀──commands───▶│ единственный владелец         │
│ призрачные ноты,       │   (typed)     │ MCP-клиентов (stdio)          │
│ HTML-audio (WAV)       │◀──events───── │ состояние шины, manifest,     │
└────────────────────────┘               │ таймаут→inspect, рендер-задачи│
                                         └───────┬───────────────┬───────┘
                                          stdio  │ JSON-RPC      │ файлы
                                                 ▼               ▼
                            audio-analyzer · midi-gen ·       workspace
                            qwen_bridge · soundcraft-plug-in  (WAV/MIDI/JSON)
```

### 6.2 Правила связи

1. **Rust-ядро — единственный владелец MCP-клиентов (stdio).** Фронтенд не
   знает про MCP/JSON-RPC: он вызывает типизированные команды ядра
   (`analyze_loop`, `generate_part`, `regenerate`, `import_accepted`,
   `run_self_check`, `get_bus_state`), ядро транслирует их в вызовы
   инструментов шины. Контракт шины (7 правил README) живёт в одном месте.
2. **Серверы НЕ переводятся на WebSocket/HTTP.** Транспорт остаётся stdio
   (конфиг уже работает, правила конфига неизменны). WS-фасад — опция
   будущего, только если UI понадобится в браузере; до того — не делаем.
3. **Pull-семантика сохраняется** (наследует DawBackend): перед действием
   ядро делает `get_session`; undo хоста — механизм отката, не подписки.
4. **События шины → ядро → Tauri events → React**: обновление карточек,
   лога, статусов — реактивно. Таймаут ≠ отказ (правило 2) реализует ядро:
   после ⏱ оно само делает `inspect` и отдаёт фронту вердикт; UI показывает
   `⏱ → inspect → ✓/✗`, никогда — молчаливый ретрай.
5. **Никакого DSP в UI-процессе** — и ядро не синтезирует: оно лишь
   оркестрирует оффлайн-рендер превью-WAV (сайдкар/хост, §10.2) и отдаёт
   фронту путь к готовому файлу для проигрывания (HTML audio).
6. **Внешний агент работает параллельно кокпиту без конфликтов протоколов**:
   ZCode подключается к тем же серверам своим транспортом; расхождение
   состояний исключается пунктом 3 (перед действием — `get_session`), а в
   инспекторе видно, кто что менял. Кокпит не «владелец» шины, а один из
   хостов — это принцип «UI = проекция шины» на топологическом уровне.

## 7. Роль агента в UI

### 7.1 Карточки-предложения, призрачные ноты, регенерация

- **Предложение = карточка на музыкальном объекте, а не сообщение в чате.**
  Под слоем баса: «Бас статичен (все ноты на сильных долях). Синкопировать?»
  `[style: syncopated ▸]` `[другой стиль ▾]` `[оставить]`. Одна строка
  rationale + confidence из контракта (§5.1) — ИИ объясняется, но не
  разговаривает.
- **Регенерация = видимый diff параметров**, а не «заново»:
  `style: basic → syncopated` — и в chips, и в логе. Пользователь всегда
  знает, **что именно** изменится; это те же параметры midi-gen v3
  (`style/voicing/variation/bars`), просто без JSON.
- **Проактивность мягкая**: агент предлагает после аудиции слоя или после
  Self-Check, кнопки — у человека. Единственный автоматический контур —
  явно включённый **автопилот** (§7.2).
- **Undo-культура**: каждое действие агента в DAW откатываемо (undo хоста),
  призрачные слои одноразовые по природе. Принять «на пробу» не страшно.

### 7.2 Три режима управления и слот «Мозг»

| Режим | Кто издаёт команды | Cockpit показывает |
|---|---|---|
| **Ручной** | Человек кнопками (без всякого LLM) | Кнопки = MCP-инструменты; лог пишет всё |
| **Агент** | Внешний агент (ZCode/Claude/Cursor) через шину | Команды светятся в инспекторе; предложения — карточками на панелях |
| **Автопилот** | Локальный мозг qwen_bridge (через Rust-ядро, §6) гоняет полный контур | Каждый шаг подсвечивается в воронке X-Ray→Стейджинг→Check; инспектор раскрывается сам; стоп-кран всегда виден |

Принципиально: **командный язык один** (MCP JSON), эмитентов может быть
много. qwen_bridge встаёт в тот же слот без изменений UI — просто ещё один
эмитент в логе (и ещё одно значение `source_tool` в контракте §5). Режим
«Ручной» гарантирует: LLM-даунтайм не выключает продукт (детерминированные
инструменты — граждане первого класса).

Автопилот — визуализация hero-сценария PRD: шаги воронки загораются по мере
исполнения, в конце — карточка Self-Check с вердиктом. Ограничения
автопилота (какие партии, сколько регенераций, импортировать ли самому)
задаются переключателями до старта.

## 8. UX-граница: что человеку, что агенту

Ось этой границы — **между человеком и ИИ** (первая ось, между
приложениями, — в §3). Философия: **«агент предлагает — человек
располагает»**, ИИ — невидимый помощник (VISION v2). Граница проведена так,
чтобы микс и финальные решения были неприкосновенны (это же не-цели
контракта DawBackend: нет микширования и редактирования нот через контракт).

| Область | Человек | Агент |
|---|---|---|
| Анализ лупа | читает интерпретации, выбирает между гипотезами (60 vs 120) | считает, толкует, предлагает |
| Настройки сессии | **согласие** (adopt loop settings — диалог) | готовит точные значения |
| Генерация партий | слушает, сравнивает версии, **принимает/отклоняет** | генерирует, параметризует, итерирует |
| Импорт в DAW | **жест «Импорт принятых»** | механика импорта, инструменты, карантин-полоса |
| Ноты | **владелец после accept** (правка в SoundCraft — единственный редактор) | не редактирует ноты (только регенерирует; до accept — призрачные) |
| Аранжировка | **структуру утверждает** (сколько тактов, что где) | предлагает (дубли, филлы, дозаполнение); v0 — не трогает |
| Микс | **только человек** (SoundCraft открыт как микшер; микс-UI не дублируем) | не лезет (нет инструментов и в контракте) |
| Мастеринг-целы | выбирает пресет (Spotify/Apple/−) | считает дельты, предлагает normalize |
| Self-Check | читает вердикт, решает что дальше | измеряет, сравнивает, объясняет |
| Уборка | — | имена файлов, версии, маркеры, manifest |

Проверка границы на прочность: агента невозможно заставить необратимо
испортить работу — всё в DAW откатываемо (undo), призрачные слои сессию не
трогают, баунсы не перезаписывают исходник (workspace, версионирование имён).

## 9. Соответствие контракту шины и ценностям PRD

### 9.1 Семь правил шины → элементы UI

| # | Правило | Как проявляется в UI |
|---|---|---|
| 1 | Workspace — граница песочницы | Стейджинг = визуализация workspace: карточки = .mid + WAV-превью + manifest.json; «UI без скрытой БД» |
| 2 | timeoutMs; таймаут ≠ отказ | Строка лога: ⏱ → авто-inspect (делает Rust-ядро, §6.2) → ✓; никакого молчаливого ретрая |
| 3 | Паника → JSON-RPC error | Ошибка = toast с причиной, а не крутящийся спиннер навсегда |
| 4 | Сессия — источник истины | Adopt Loop Settings = явный диалог; призрачные ноты живут в UI до accept (второго редактора нет, §3.3); embed_tempo=false виден в chips |
| 5 | Lifecycle движка | Прогресс «поднимаю редактор DAW…» (прогрев ~8 с) — как wake-up паттерн; retry с видимой попыткой № |
| 6 | duplicate_extend экспоненциально | Кнопка-интент «8 тактов» (v1) прячет ceil(log2 N); в логе — честные вызовы |
| 7 | Self-Check: relative-key + после аранжировки | Бейдж «A minor ≡ C major (отн.)»; Check запускается по кнопке после баунса готовой аранжировки |

### 9.2 Ценности PRD → механизмы UI

| Ценность | Механизм |
|---|---|
| Скорость | Анализ 55–91 мс — карточка X-Ray мгновенно; регенерация < 1 с; WAV-превью вместо 10-с импортов |
| Редактируемость (главный дифференциатор) | accept = призрачная нота материализуется в обычную MIDI-дорожку DAW; «владение нотами» начинается с accept; превью ничего не портит |
| Музыкальная глубина | Chips параметров = управляемая глубина (style/voicing/variation); история версий поощряет итерации до «хочу оставить» |
| Прозрачность | Инспектор шины = вся деятельность агента; кнопка = инструмент; rationale + source_tool в каждом suggestion; open-source стек без скрытых API |

### 9.3 Acceptance Rate (PRD §4) → жест UI

Полный механизм — §5.3: контракт suggestion + логируемые accept/reject в
manifest = инструментация метрики с первого дня; жест честный (решение
принимает человек явной кнопкой), данные локальные.

## 10. Технологический стек: Tauri + React (данность VISION v2)

### 10.1 Решение и отклонённые альтернативы

Стек зафиксирован VISION v2: **Tauri + React** — Rust-ядро (Tauri main)
+ системный WebView (без Chromium-тарбола) + React-фронтенд.

Нативные Rust-UI (egui/iced) — **рассмотрены и отклонены**: их единственное
решающее преимущество перед WebView — real-time DSP прямо в процессе UI —
запрещено железным правилом «никакого DSP в UI-процессе», а по графике
(спектры, хромаграммы, piano-roll с призрачными нотами — canvas-примитивы)
и скорости разработки web-стек сильнее. Подробный разбор был в v0.2 —
устарел с принятием решения, в тело документа не возвращается.

### 10.2 Архитектурные правила стека и риски WebView

**Железные правила (VISION v2):**
1. **Никакого DSP в UI-процессе.** Единственный звук, который издаёт кокпит
   — **проигрывание отрендеренного WAV** (HTML audio). Рендер превью — вне
   UI. Решено (мейнтейнер, собрание №1): первым — **сайдкар GM-синт** (.mid →
   .wav через GM-soundfont, subprocess, оффлайн) для быстрых итераций;
   headless-баунс SoundCraft / карантинная полоса остаётся WYSIWYG-ступенью
   (§4.2). Лицензионный гейт soundfont + FluidSynth (LGPL-2.1) для MIT-репо
   — разведка OSS-разведки (в работе).
2. **WebKitGTK-Linux тестируем на первой неделе.** Кокпит обязан работать
   на Debian разработчика — это платформа разработки. Чек-лист спайка:
   шрифты/рендер текста, латентность и стабильность HTML audio (gapless-
   луп!), drag-and-drop файлов из файлового менеджера, always-on-top окно,
   потребление памяти. **Fallback (из VISION v2):** тот же React-бандл как
   локальный web-UI в браузере + Tauri-шелл позже — архитектура «UI =
   проекция шины» и Rust-ядро не меняются, меняется только оболочка.

**Прочие правила стека:**
- IPC-контракт типизирован на стороне ядра (commands/events, §6.2);
  фронтенд без прямого доступа к MCP.
- Манифест и все артефакты — в workspace (правило 1): кокпит переносим
  между машинами копированием папки.
- SoundCraft-UI остаётся открытым как микшер — окно кокпита не содержит ни
  одного фейдера (§3.2).

### 10.3 Этапность (утверждена мейнтейнером, собрание №1 — основа ТЗ UI-модуля)

1. **Этап 1 (v0) — AI-кокпит, read-only аранжировка:** Tauri-скаффолд +
   WebKitGTK-спайк (неделя 1); Loop X-Ray-карточка; стейджинг с призрачными
   нотами (контракт §5.1: notes в формате midi_io / rationale / confidence /
   source_tool), WAV-превью (сайдкар GM-синт), chips-регенерация;
   Piano-roll-просмотр (read-only, минимальный: zoom, без velocity-lane);
   «Импорт принятых»; инспектор шины; manifest + логирование accept/reject
   с первого дня.
2. **Этап 2 — замыкание контора:** Self-Check-панель (compare-
   визуализация), accept-метрики в manifest, экспорт статичного HTML-отчёта.
3. **Этап 3 — аранжировочные интенты (выход из read-only):** «заполнить N
   тактов» (дубль-рецепт), сцены-комбинации, карантинный WYSIWYG-прогон.
4. **Этап 4 — мозг:** визуализация автопилота qwen_bridge (воронка
   hero-сценария), ограничения автопилота, стоп-кран.

## 11. Риски и открытые вопросы

**Риски:**
1. **Два окна** (рассеивание внимания). Митигация: компактный режим-полоса
   (только статус+транспорт); типовой лэйаут «DAW слева, кокпит справа» как
   пресет; всё критичное дублируется кнопками на карточках.
2. **WebKitGTK-кверки на Linux** (первая платформа). Митигация: спайк
   первой недели (§10.2), готовый fallback = локальный web-UI без потери
   архитектуры.
3. **Превью-синт ≠ финальный тембр** (человек принял «не тот» бас).
   Митигация: двухступенчатая аудиция (§4.2), честная пометка «превью-
   тембр», WYSIWYG-прогон в карантине.
4. **Dual source of truth** (призрачные ноты vs сессия). Митигация: §3.3 —
   до accept / после accept, атомарный переход, manifest.
5. **Scope explosion** (кокпит тянет стать DAW). Митигация: v0 = read-only
   аранжировка, ни одного фейдера, не-цели DawBackend действуют и на UI.
6. **Дрейф MCP-API SoundCraft (pre-alpha).** Митигация: кокпит говорит только
   словарём DawBackend, адаптер амортизирует.
7. **Acceptance Rate без пользователей** — жест есть, данных нет.
   Митигация: PRD §4 уже имеет авто-прокси (voice motion, variety,
   вариативность); manifest готов к сбору с первых бета-тестеров волны 1.

**Решения L2T team по бывшим открытым вопросам (закрыты на собрании №1,
2026-11-22; внесены в текст выше):**
1. Этапность §10.3 — утверждена как есть (Self-Check остаётся на этапе 2;
   основа ТЗ UI-модуля).
2. Формат manifest — контракт suggestion §5.1 за основу (см. §5.3).
3. Превью-рендер — сайдкар GM-синт (вариант (а)) первым; SoundCraft-баунс —
   WYSIWYG-ступень (§10.2).
4. Piano roll v0 — минимальный: zoom, без velocity-lane (§3.1, §4.2, §10.3).
